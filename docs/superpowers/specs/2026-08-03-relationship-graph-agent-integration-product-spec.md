# Relationship Graph Agent Integration Product Spec v0.1

## 1. 产品定位与平台约束

- 目标用户入口只有浏览器和 PWA，不提供原生 App。
- 统一前端壳使用 agent-chat-ui / Web 端聊天界面，所有功能都在浏览器或 PWA 中运行。
- 关系图谱、联系人维护、草稿确认、路径查找、导入等能力都以 Web 交互为主。
- 任何“本地能力”都必须通过浏览器可访问的方式暴露，例如本地服务、受控 bridge、浏览器扩展或 HTTPS 接口，而不是依赖独立桌面应用。

## 2. 核心产品目标

1. 让用户在同一个会话框中完成“普通聊天 + 关系维护 + 关系检索”。
2. 让用户画像、关系上下文、智囊团 skill 在所有相关会话中自动挂载。
3. 把关系图谱从独立页面改造成消息流中的结果卡片 + 右侧面板中的 artifact 展示。
4. 把写入行为变成“草稿 → 确认 → 写入”的结构化流程。

## 3. 用户场景

### 3.1 通用聊天
- 用户可以正常聊天、总结、写作、提纲、邮件草拟。
- 只要涉及“人、关系、互动、跟进、路径、机会”时，系统自动挂上关系上下文与画像上下文。

### 3.2 关系检索
- 用户输入：
  - “谁在上海做地产，和我关系比较近？”
  - “上次聊过融资的人里，还没跟进的有谁？”
- 系统返回结果卡片，并在右侧面板展示详情/路径/草稿入口。

### 3.3 关系写入
- 用户输入：
  - “刚认识了一个人在做园区项目”
  - “刚和张明聊了融资”
- 系统生成草稿，用户确认后写入联系人、互动记录或关系链路。

## 4. 交互规格

### 4.1 统一输入入口
- 入口位于聊天主输入框。
- 允许输入文本、附件、语音转文字、图片 OCR。
- 输入后由 LangGraph/Orchestrator 判断是否进入关系域子图、council skill、普通聊天或工具动作。

### 4.2 消息流
- 普通对话：纯文本消息。
- 工具结果：result card / draft card / path card。
- 需要确认的操作：confirmation card，支持确认、修改、取消。

### 4.3 右侧面板
- 图谱、联系人详情、导入预览、审计提示等统一放在右侧面板。
- 消息流只展示摘要、状态和操作入口。

## 5. 记忆与上下文规格

### 5.1 用户画像
- 在注册期强约束完成。
- 后续所有会话默认加载。
- 画像包含：价值观、偏好、行业边界、决策风格、关键约束。

### 5.2 关系上下文
- 联系人、关系、互动记录、最近跟进、敏感级别、路径信息。
- 只在相关请求中挂载，避免全量注入。

### 5.3 智囊团与虚拟人物
- 每个智囊团成员都是一个虚拟人物。
- 当用户通过 @ 或明确要求某位成员生成报告、邮件、分析时，使用对应 skill。
- relation-graph 上下文作为 skill 输入的一部分。

## 6. 事务边界

### 6.1 可自动执行
- 查询、摘要、草稿生成、路径规划、候选排序、邮件/消息草稿生成。

### 6.2 必须确认
- 新增联系人、修改关系、写入互动记录、发出真实消息、访问高敏感字段、执行外部工具动作。

### 6.3 不可回滚
- 真实发送消息、创建正式事项、发起外部系统动作。

## 7. 模块拆分

### 7.1 前端模块
- chat shell：消息流、输入框、确认卡片。
- artifact panel：图谱/详情/导入预览。
- relationship widget：联系人查询结果、路径、草稿确认。

### 7.2 编排层
- LangGraph supervisor：意图分类、上下文拼装、多意图链、事务控制。
- subgraph：relationship-graph、profile、council、desktop/tool bridge。

### 7.3 关系域服务
- persons / relationships / interactions / graph / nlq / path / import / sensitivity。
- 继续复用现有关系图谱领域能力，先服务化再接入编排层。

### 7.4 本地能力
- 仅在浏览器/PWA 可访问的场景下接入。
- 目标不是“桌面 App”，而是“浏览器可调用的本地桥接/服务”。
- 高敏感数据仍然以受控桥接方式接入，默认只允许只读、白名单查询。

## 8. 第一阶段交付内容

1. 基于现有关系图谱能力，提供一个可运行的 agent 工作台。
2. 支持普通自然语言查询、联系人结果展示、草稿确认。
3. 右侧 panel 支持 artifact 展示。
4. 为后续接入 profile、council 与本地 bridge 预留扩展点。

## 9. 技术实现顺序

1. 先建立前端 chat shell 与 artifact panel。
2. 连接现有 NLQ / 草稿确认能力。
3. 再接入 profile context 与 council skill 入口。
4. 最后接入本地 bridge 与高敏感数据受控查询。
