个人关系图谱应用设计文档

更新方向：远程 Linux 服务端承载核心服务，Windows 和手机作为客户端。

1. 项目背景

日常工作中需要维护大量弱关系联系人：今天认识的某公司工程师、经谁介绍、聊了什么、后续是否需要跟进。传统通讯录只能存基础信息，无法表达“经谁介绍”“聊过什么话题”“当前状态”“谁能帮上忙”等关系维度。因此需要一款以“人”为中心、以“关系”和“互动记录”为线索的个人关系图谱应用。

最新目标已经从“Windows 本地电脑同时承担客户端和服务端”调整为：远程 Linux 服务器承载主要控制逻辑、数据服务、AI/ASR/OCR 能力；Windows 电脑和手机都作为客户端访问服务端。这样更符合多端长期使用、低客户端部署成本和后续扩展需求。

2. 目标

构建一款以 Web/PWA 为优先形态的个人关系图谱系统，核心能力包括：

  • 维护联系人基础信息、关系链路、互动记录。
  • Windows 电脑和手机都作为客户端，角色尽量一致。
  • 服务端统一负责业务逻辑、数据库、AI 信息抽取、语音转文字、OCR 和自然语言查询。
  • 支持文字、语音、图片等多种录入方式。
  • 支持自然语言查询，从数据库中检索匹配联系人及互动摘要。
  • 以图谱方式可视化人和人之间的关系。
  • 对敏感联系人和敏感字段提供脱敏展示、访问控制、审计日志和加密存储。
  • 支持后续扩展为手机 PWA / App、Windows 桌面壳、浏览器插件或其他客户端。

3. 典型用户场景

场景 1：初次认识并记录

用户今天认识了某公司的工程师，打开手机或 Windows 客户端，新增联系人，填写姓名、电话、邮箱、公司、职位，标记“经谁介绍认识”，并记录第一次见面聊的内容。

场景 2：持续维护沟通记录

若干天后再次沟通，用户通过文字或语音追加一条互动记录。客户端负责采集和展示确认界面，服务端负责语音转文字、摘要、话题、待办和人物提及提取，用户确认后写入数据库，并更新“上次互动”和“当前状态”。

场景 3：自然语言查询

用户打开应用直接提问：

  • “谁在上海做地产，和我关系比较近？”
  • “上次聊过融资的人里，还没跟进的有谁？”
  • “这个懂车帝的投标，谁能帮上忙？”
  • “最近 3 个月没联系但标记了‘待跟进’的人有哪些？”

系统返回匹配结果、上次互动摘要和建议下一步。

场景 4：名片扫描录入

用户在手机端拍照，或在 Windows 端上传名片图片/截图。服务端 OCR 识别文字后，再由 LLM 整理成结构化联系人信息，客户端展示候选字段和疑似重复联系人，用户确认后保存。

场景 5：多端一致访问

用户在手机上录入沟通内容，晚上在 Windows 电脑上继续整理联系人和关系图谱。所有客户端都通过 HTTPS 访问同一套远程 Linux 服务端，数据不需要在 Windows 与手机之间额外同步。

4. 架构设计

4.1 整体形态

目标架构调整为：远程 Linux 服务器是核心，Windows 和手机都是客户端。

Windows 浏览器 / PWA / 可选桌面壳
          ↓ HTTPS
手机浏览器 / PWA / 可选原生 App
          ↓ HTTPS
远程 Linux Server
  ├── Web API
  ├── 身份认证 / 权限控制
  ├── 业务服务层
  │   ├── 联系人管理
  │   ├── 互动记录管理
  │   ├── 关系图谱构建
  │   ├── 自然语言查询（NLQ）
  │   ├── 语音转文字（ASR）
  │   └── 名片 OCR / 图片处理
  ├── 数据库（PostgreSQL 优先，个人 MVP 可用 SQLite）
  ├── 字段级加密 / 备份加密
  ├── LLM 服务（Ollama / vLLM / 其他兼容服务）
  ├── Whisper / faster-whisper
  ├── OCR 服务（PaddleOCR / Tesseract）
  └── 日志、审计、备份与监控

4.2 客户端职责

  • 登录、会话保持和二次确认。
  • 联系人、互动记录、关系图谱、自然语言查询等页面展示。
  • 文字输入、录音、拍照、上传图片/音频。
  • 展示服务端返回的识别结果、联系人候选和歧义确认。
  • 在用户确认后提交入库。

客户端不直接访问数据库，不直接保存长期明文业务数据。离线能力可作为后续增强，不放入第一阶段。

4.3 服务端职责

  • 提供统一 REST API 或 GraphQL API。
  • 管理数据库连接、迁移、备份和加密。
  • 执行核心业务逻辑和访问控制。
  • 执行 ASR、OCR、LLM 抽取、NLQ 意图解析和结果生成。
  • 维护联系人、关系、互动记录、实体提及、任务和审计日志。
  • 提供结构化日志和运行状态观测能力。

4.4 Tauri 的定位

Tauri 不再作为核心架构依赖。后续如果需要 Windows 桌面体验，可以把 Tauri 作为“可选桌面壳”：内嵌同一套 React Web 前端，仍然通过 HTTPS 调用远程 Linux 服务端，不承载数据库和核心业务逻辑。

4.5 部署与运行环境

  • 生产服务端：Linux Server，推荐 Docker Compose 部署。
  • 客户端：Windows 浏览器/PWA、手机浏览器/PWA；后续可封装移动 App 或桌面壳。
  • 网络：公网或内网 HTTPS 访问，必须启用认证和访问控制。
  • 数据存储：服务端数据库集中存储，定期加密备份。
  • AI 能力：优先服务端集中部署，客户端不强制安装 Ollama、Whisper、OCR 等依赖。

6. 核心功能

6.1 联系人名片视图

  • 姓名、昵称/代称、公司、职位。
  • 认识背景。
  • 关系强度。
  • 资源标签。
  • 敏感级别。
  • 上次互动时间和摘要。
  • 当前状态。
  • 下一步计划。
  • 备注。

高敏感联系人默认脱敏展示，查看详情需要二次确认。

6.2 语音录入互动记录

语音入口在手机和 Windows 客户端都需要支持，但识别逻辑放在服务端。

  1. 用户在手机或 Windows 客户端录音/上传音频。
  2. 客户端将音频通过 HTTPS 上传到服务端。
  3. 服务端创建 ImportTask 和 MediaAsset。
  4. 服务端使用 Whisper / faster-whisper 转文字。
  5. 服务端使用 LLM 提取人物、话题、摘要、待办事项。
  6. 服务端匹配别名库，识别“老张”等模糊代称。
  7. 若匹配到多个联系人，按“最近联系 + 上下文 + 关系强度”排序，返回候选列表。
  8. 客户端展示转写文本、摘要、候选联系人和待办事项。
  9. 用户确认/修正后，服务端保存 Interaction 和 EntityMention，更新联系人状态。
  10. 原始音频默认处理后删除；如用户选择留档，则加密保存。

6.3 名片扫描录入

名片扫描入口在手机和 Windows 客户端都需要支持，但 OCR 和结构化放在服务端。

  1. 用户在手机端拍照，或在 Windows 端上传图片/截图。
  2. 客户端将图片通过 HTTPS 上传到服务端。
  3. 服务端创建 ImportTask 和 MediaAsset。
  4. 服务端使用 OCR 提取文字。
  5. 服务端使用 LLM 整理为结构化字段：姓名、公司、职位、电话、邮箱、地址、备注。
  6. 服务端执行查重和相似联系人匹配。
  7. 客户端展示识别结果和候选联系人。
  8. 用户确认后创建或更新 Person。
  9. 原始图片默认处理后删除；如用户选择留档，则加密保存。

6.4 关系图谱可视化

  • 节点：联系人。
  • 边：介绍关系、共同话题、共同参与的项目等。
  • 支持按关系强度、资源标签、敏感级别筛选。
  • 支持点击节点查看联系人名片。
  • 高敏感节点默认以代称展示，必要时仅显示存在关系而不显示明文信息。

6.5 自然语言查询（NLQ）

自然语言查询不应让 LLM 直接生成 SQL。推荐流程：

  1. 用户在搜索框用自然语言提问。
  2. 服务端将问题解析为 QueryIntent 中间表示。
  3. 应用层对 QueryIntent 做白名单校验：字段、枚举、limit、排序均受控。
  4. 服务端使用参数化 SQL 或安全查询构造器查询数据库。
  5. 服务端按关系强度、最近互动、话题匹配度等规则重排。
  6. LLM 只负责辅助解释和生成自然语言摘要，不直接接触任意 SQL 生成权限。
  7. 客户端展示匹配联系人、上次互动摘要、当前状态和建议下一步。

初版支持的查询类型

类型示例
按标签/地域/关系强度查人“谁在上海做地产，和我关系比较近？”
按互动状态查人“最近 3 个月没联系但标记了待跟进的人有哪些？”
按话题查人“上次聊过融资的人里，还没跟进的有谁？”
按项目/需求匹配资源“这个懂车帝的投标，谁能帮上忙？”
组合条件“做设计、关系强、最近一个月联系过的上海人”

6.6 多端客户端

第一阶段优先 Web/PWA：Windows 使用浏览器访问 Web 应用，后续可封装桌面壳；手机使用响应式 Web/PWA，后续可封装原生 App。所有客户端共享同一 API，不为不同端维护不同业务逻辑。

7. 安全设计

7.1 身份认证与访问控制

  • 所有客户端必须登录后访问。
  • 服务端使用短期 access token + 可撤销 refresh token。
  • 高敏感数据查看需要二次确认，例如重新输入密码、WebAuthn、TOTP 或一次性确认。
  • 后续如支持多人使用，需要引入用户、角色、权限和资源隔离。

7.2 传输安全

  • 所有公网访问必须使用 HTTPS。
  • 上传音频、图片和查询请求不得走明文 HTTP。
  • API 默认启用 CSRF/CORS 策略，生产环境只允许可信域名。

7.3 数据加密

推荐第一阶段采用“服务端可处理明文的字段级加密”方案：

  • 数据库所在磁盘启用服务端磁盘加密或云盘加密。
  • 电话、邮箱、备注、沟通原文、摘要、关系说明、下一步计划等字段加密存储。
  • 标签、状态、时间、关系强度等用于检索的低敏结构化字段可保留明文或保存规范化索引。
  • 原始音频和图片默认处理后删除；如保留，必须加密保存。
  • 数据库备份必须加密，并定期验证可恢复性。

暂不建议第一阶段采用完整端到端加密，因为服务端需要执行 OCR、ASR、LLM 抽取、NLQ 和关系推理。后续如隐私要求提高，可对部分字段逐步引入客户端加密和可搜索索引。

7.4 敏感级别访问控制

敏感级别列表展示详情查看自然语言查询
低正常显示正常显示正常返回
中可显示代称和部分信息点击后显示完整信息返回结果但敏感字段脱敏
高显示代称 + 脱敏提示需二次确认默认折叠，提示“存在 N 位高敏感联系人，是否查看”

7.5 审计与日志可观测性

日志目标是方便排障、审计和性能观察，同时避免泄露隐私。

允许记录：请求 ID、用户 ID、接口名、状态码、耗时、查询类型、结果数量、候选数量、音频/图片大小、处理耗时、任务状态、敏感级别、二次确认状态、错误摘要和错误类型。

禁止记录：密码、token、密钥、电话、邮箱、完整姓名、完整沟通内容、完整语音转写文本、原始名片图片内容、OCR 全文、用户完整自然语言问题。

9. MVP 范围

包含

  • Linux 服务端基础 API。
  • Web/PWA 前端，可在 Windows 和手机浏览器访问。
  • 用户登录和基础会话管理。
  • 联系人 CRUD 和名片视图。
  • 关系链路维护。
  • 文字录入互动记录。
  • 语音上传/录音入口，服务端 ASR，用户确认后入库。
  • 图片上传/拍照入口，服务端 OCR，用户确认后创建/更新联系人。
  • 互动记录列表和详情。
  • 关系图谱可视化基础版本。
  • 自然语言查询限定查询类型。
  • 敏感级别访问控制。
  • 字段级加密和加密备份设计落地。
  • 隐私安全的结构化日志和审计日志。

不包含

  • 完整原生手机 App。
  • 复杂多用户组织权限系统。
  • 完整端到端加密。
  • 离线编辑和多端冲突合并。
  • 自动化公网域名、证书和服务器采购流程。
  • 复杂的关系权重自动计算。
  • 与微信、通讯录、邮件等第三方系统深度集成。

10. 风险与待决策事项

风险说明应对
远程服务端隐私风险数据集中在 Linux 服务器，安全边界从本地电脑转为服务端HTTPS、认证、字段级加密、审计日志、加密备份、最小权限部署
LLM 解析不稳定自然语言查询和信息抽取可能误判使用 QueryIntent 中间层、白名单校验、用户确认、固定查询降级
ASR/OCR 资源消耗语音和图片识别需要 CPU/GPU 资源使用异步任务队列，限制文件大小，支持轻量模型和任务状态查询
媒体文件泄露音频和名片图片包含高敏感信息默认处理后删除；如留档，必须加密保存并审计访问
多端体验差异手机拍照录音更方便，Windows 上传整理更方便统一 API 和确认流程，按端优化采集入口，不分叉业务逻辑
模糊代指消解准确率“老张”等代称容易匹配错误低置信度强制人工确认，保留用户修正记录
部署复杂度Linux 服务端涉及 Docker、HTTPS、模型服务MVP 先支持单机 Docker Compose，AI 能力允许可选启用

11. 后续演进方向

  1. Web/PWA 优先完善手机端体验。
  2. 增加服务端异步任务队列，用于 ASR、OCR、LLM 抽取。
  3. 增加更完整的 NLQ 查询类型和解释能力。
