个人关系图谱应用设计文档 v1.3

版本：v1.3

日期：2026-07-30

本版本用途：在 v1.2 技术需求文档基础上，补齐分级存储、统一自然语言入口、关系推断、路径生成、批量导入、提醒机制和 Open 问题。

1. 项目背景

日常工作中需要维护大量弱关系联系人：今天认识的某公司工程师、经谁介绍、聊了什么、后续是否需要跟进。传统通讯录只能存基础信息，无法表达“经谁介绍”“聊过什么话题”“当前状态”“谁能帮上忙”等关系维度。

本项目目标是把个人或团队核心成员脑子里的人脉资产，整理成可以持续维护、自然语言检索和图谱化调用的私有知识库。

相比早期“Windows 本地电脑同时承担客户端和服务端”的方向，v1.3 的目标架构调整为：

  • 中低敏感数据：通过远程 Linux 服务端提供 Web/PWA 多端访问能力。
  • 高敏感数据：原则上本地加密保存，不上传服务端。
  • Windows 端：既可以访问远程服务端，也可以承担高敏感本地数据访问能力。
  • 手机端：优先访问远程中低敏感数据；是否访问高敏感数据暂不做承诺。

其中“高敏感数据只在本地保存会带来换电脑丢失风险”目前标记为 Open，需要后续进一步评估备份、迁移和加密恢复方案。

2. 目标

构建一款以 Web/PWA 为优先形态、可扩展 Windows 增强客户端的个人关系图谱系统，核心能力包括：

  • 维护联系人基础信息、关系链路、互动记录和下一步跟进。
  • 通过统一自然语言入口完成录入、更新、检索和路径查询。
  • 支持文字、语音、名片图片、聊天记录和表格等多种录入方式。
  • 支持自然语言查询，从数据库中检索匹配联系人及互动摘要。
  • 以图谱方式可视化人和人、人与项目、人与机会之间的关系。
  • 支持项目/机会场景下的关联路径生成。
  • 对不同敏感级别的数据采用不同存储路径、展示策略、访问控制和审计日志。
  • 支持后续扩展为手机 PWA / App、Windows 桌面壳、浏览器插件或其他客户端。

3. 核心设计原则

3.1 低摩擦维护优先

长期核心交互不是表单，而是自然语言和语音更新。

用户不应为了维护关系而被迫填写复杂表单。第一版可以保留简化表单作为兜底和调试入口，但主流程应是：

用户说一句话或输入一段文字
→ 系统判断意图
→ LLM/规则引擎提炼结构化草稿
→ 用户确认或修正
→ 写入联系人、互动记录、关系或项目数据

3.2 LLM 做解读，不直接做关键写入决策

需要 LLM 来理解自然语言、提取字段、生成摘要、识别代称、整理名片和解释查询结果。但 LLM 的角色是“辅助解读和生成候选结果”，不是直接操作数据库的主体。

关键原则：

  • LLM 可以生成结构化草稿。
  • 应用层负责字段白名单、枚举校验、权限判断和写入控制。
  • 用户对新增联系人、修改字段、合并联系人、确认关系等关键动作有最终确认权。
  • NLQ 不允许 LLM 直接生成任意 SQL，应使用 QueryIntent 中间层。

3.3 分级存储优先

不同敏感级别的数据走不同存储路径：

敏感级别内容示例存储方式手机可访问
高敏感核心合伙人、政商关系、家族关系、高敏感互动记录本地加密，原则上不上传服务端暂不支持
中敏感行业人脉、潜在合作方、一般商务互动远程服务端，字段级加密支持
低敏感公开信息、普通行业联系人远程服务端支持

Open：高敏感数据如果只保存在一台电脑上，换电脑、电脑损坏或重装系统时存在数据丢失风险。后续需要确认是否采用加密备份、用户自持恢复密钥、私有云同步、移动硬盘备份或其他方案。

4. 典型用户场景

4.1 初次认识并记录

用户刚认识一个人，打开手机或 Windows 客户端，说：

“刚认识了一个人，叫张明，是做地产融资的，上海人，老李介绍的，后面可能能聊园区项目。”

系统识别为“新建联系人”，提取姓名、标签、城市、介绍人、潜在合作方向和当前状态，展示关系卡片草稿。用户确认后保存。

4.2 持续维护沟通记录

用户和某个人又沟通了一些事情，不需要打开复杂表单，只要说：

“刚和张明聊了，他说下周来上海，可以约他聊一下园区项目。”

系统识别为“更新已有联系人互动记录”，自动匹配张明。如果“张明/老张”有多个候选，系统展示候选列表，用户确认后保存 Interaction，并更新上次互动时间、摘要、话题和下一步行动。

4.3 查询时顺手更新

用户查询某个联系人时，系统发现上次互动时间较久，可主动问：

“你上次和张明的互动记录是 45 天前，最近有联系吗？”

用户回复后，系统自动追加互动记录。这是语音打标记之外的兜底维护方式。

4.4 自然语言查询

用户打开应用直接提问：

  • “谁在上海做地产，和我关系比较近？”
  • “上次聊过融资的人里，还没跟进的有谁？”
  • “这个懂车帝的投标，谁能帮上忙？”
  • “最近 3 个月没联系但标记了‘待跟进’的人有哪些？”

系统返回匹配联系人、上次互动摘要、当前状态、建议下一步和必要的关系路径。

4.5 项目路径生成

用户输入：

“这个园区项目，我通过谁能联系到王局长？”

系统在关系图谱中查找从“我”到目标人的可行路径，优先选择强关系和最近有互动的节点，输出推荐路径、依据和建议行动。

5. 架构设计

5.1 整体形态

v1.3 采用“远程服务端 + 本地高敏感库”的分级架构。

手机浏览器 / PWA
  └── HTTPS 访问远程服务端
      └── 中低敏感数据、AI、ASR、OCR、NLQ

Windows 浏览器 / PWA
  └── HTTPS 访问远程服务端
      └── 中低敏感数据、AI、ASR、OCR、NLQ

Windows 增强客户端（Tauri 或本地助手，Open）
  ├── HTTPS 访问远程服务端
  └── 本地 SQLCipher 高敏感数据库

远程 Linux Server：

Linux Server
  ├── Web API
  ├── 身份认证 / 权限控制
  ├── 业务服务层
  │   ├── 联系人管理
  │   ├── 互动记录管理
  │   ├── 项目/机会管理
  │   ├── 关系图谱构建
  │   ├── 关系推断和确认
  │   ├── 自然语言查询（NLQ）
  │   ├── 统一自然语言入口 Intent Router
  │   ├── 语音转文字（ASR）
  │   └── 名片 OCR / 图片处理
  ├── 数据库（PostgreSQL 优先，个人 MVP 可用 SQLite）
  ├── 字段级加密 / 备份加密
  ├── LLM 服务（Ollama / vLLM / OpenAI-compatible API）
  ├── Whisper / faster-whisper
  ├── OCR 服务（PaddleOCR / Tesseract）
  └── 日志、审计、备份与监控

5.2 客户端职责

手机和普通 Web/PWA 客户端：

  • 登录、会话保持和二次确认。
  • 展示联系人、互动记录、关系图谱、自然语言查询页面。
  • 采集文字、录音、拍照、上传图片/音频。
  • 展示服务端返回的识别结果、联系人候选和歧义确认。
  • 访问中低敏感数据。

Windows 增强客户端：

  • 具备普通客户端的全部能力。
  • 访问本地高敏感 SQLCipher 数据库。
  • 在本机完成高敏感数据的解密、脱敏展示和二次确认。
  • 在本机合并展示“远程中低敏感结果 + 本地高敏感结果”。

Open：Windows 增强客户端具体采用 Tauri，还是采用浏览器 + localhost helper，需要后续确认。考虑到现有原型已有 Tauri 基础，第一阶段可优先评估 Tauri。

5.3 服务端职责

远程 Linux 服务端负责：

  • 提供统一 REST API，后续可扩展 GraphQL。
  • 管理中低敏感数据库连接、迁移、备份和加密。
  • 执行核心业务逻辑和访问控制。
  • 执行 ASR、OCR、LLM 抽取、NLQ 意图解析和结果生成。
  • 维护联系人、关系、项目、互动记录、实体提及、提醒和审计日志。
  • 提供结构化日志和运行状态观测能力。

服务端原则上不接收、不持久化高敏感联系人数据。

Open：是否允许服务端保存高敏感数据的脱敏索引、不可逆摘要或加密备份，需要进一步确认。

5.4 Tauri 的定位

Tauri 在 v1.3 中不再只是可选桌面壳，也可能承担 Windows 端高敏感本地库访问能力。

推荐暂定：

  • Web/PWA 是中低敏感多端访问的主客户端。
  • Tauri 是 Windows 增强客户端候选方案。
  • Tauri 内嵌同一套 React 前端。
  • 中低敏感数据通过 HTTPS 调用远程服务端。
  • 高敏感数据通过本地 SQLCipher 保存和读取。

这样可以在多端便利性和高敏感数据本地化之间取得相对稳妥的平衡。

6. 统一自然语言入口

6.1 入口定位

应用应提供一个主输入框，支持文字和语音。用户可以直接输入自然语言，不需要先选择“新增”“查询”“更新”或“路径”。

系统通过 Intent Router 判断意图：

意图示例处理方式
create_person“刚认识了张明，做地产融资”生成联系人草稿
update_person“张明现在去了新公司”生成字段更新草稿
add_interaction“刚和张明聊了园区项目”追加互动记录
search_people“谁在上海做地产？”走 QueryIntent 检索
find_path“我通过谁能联系到王局长？”生成关系路径
create_project“新建一个懂车帝投标机会”生成项目/机会草稿
import_record“这段微信聊天帮我整理一下”创建导入任务

6.2 判断规则

初版可采用规则 + LLM 的混合方式：

  • 疑问句或条件描述：优先识别为检索。
  • 已有联系人姓名 + 时间/事件描述：优先识别为互动更新。
  • 未知人名 + 职业/标签/背景描述：优先识别为新建联系人。
  • 包含“谁能帮忙”“通过谁联系”“怎么搭上线”：优先识别为路径生成。
  • 置信度低时不直接写入，要求用户选择意图。

6.3 表单定位

第一版可以保留表单，但表单不是核心体验。

表单主要用于：

  • 管理员或早期测试时快速补数据。
  • 用户对 AI 提炼结果进行精确修正。
  • LLM 不可用时的兜底录入。
  • 数据字段较复杂时的高级编辑。

产品主流程应是自然语言/语音 → 结构化草稿 → 用户确认。

8. 核心功能

8.1 联系人名片视图

每个联系人展示为一张名片，包含：

  • 姓名、昵称/代称、公司、职位。
  • 认识背景和认识渠道。
  • 介绍人或关联来源。
  • 对方核心资源/能力。
  • 我能为对方提供什么。
  • 关系强度。
  • 资源标签。
  • 敏感级别。
  • 上次互动时间和摘要。
  • 当前状态。
  • 下一步计划。
  • 备注和核实建议。

高敏感联系人默认脱敏展示，查看详情需要二次确认。

8.2 自然语言录入和更新

主流程：

  1. 用户输入文字或语音。
  2. 系统识别意图。
  3. LLM 提取结构化字段、摘要、话题、待办和可能的人物提及。
  4. 系统按字段白名单和枚举规则校验。
  5. 客户端展示草稿。
  6. 用户确认、修正或取消。
  7. 服务端或本地库写入数据。

这部分对应代码也需要随设计调整：现有联系人表单和互动表单应逐步让位给统一自然语言入口，后端需要增加 Intent Router、草稿确认和字段更新 API。

8.3 语音录入互动记录

语音入口在手机和 Windows 客户端都需要支持。

  1. 用户录音或上传音频。
  2. 系统创建 ImportTask 和 MediaAsset。
  3. ASR 转文字。
  4. LLM 提取人物、话题、摘要、待办事项。
  5. 系统匹配别名库，识别“老张”等模糊代称。
  6. 若匹配到多个联系人，按最近联系、上下文、关系强度排序，返回候选列表。
  7. 用户确认/修正后保存 Interaction 和 EntityMention。
  8. 原始音频默认处理后删除；如用户选择留档，则加密保存。

8.4 名片扫描录入

名片扫描入口在手机和 Windows 客户端都需要支持。

  1. 用户拍照或上传图片。
  2. 系统创建 ImportTask 和 MediaAsset。
  3. OCR 提取文字。
  4. LLM 整理为结构化字段。
  5. 系统执行查重和相似联系人匹配。
  6. 用户确认后创建或更新 Person。
  7. 原始图片默认处理后删除；如留档，则加密保存。

8.5 微信聊天记录导入

P1 支持用户粘贴一段微信聊天记录，由系统判断是否需要更新或新建联系人卡片。

  • 识别联系人，更新互动记录。
  • 提取话题、摘要、待办事项。
  • 聊天记录中出现未在图谱中的人名且与具体事项相关联时，提示用户是否新建。
  • 不自动保存未确认的敏感内容。

8.6 CSV / Excel / vCard 批量导入

批量导入支持：

  • CSV。
  • Excel .xlsx。
  • 手机通讯录 vCard。
  • 微信通讯录暂列 P2 或待技术评估。

Excel 字段和数据库不匹配时，不应直接导入失败，而是进入字段映射流程：

  1. 系统读取表头和前几行样例。
  2. 自动猜测字段映射，例如“手机”“联系电话”映射到 phone。
  3. 未识别字段进入“自定义字段/备注/忽略”选择。
  4. 用户确认字段映射。
  5. 系统做格式校验和重复检测。
  6. 展示导入预览，包括新增、可能重复、无法识别的记录。
  7. 用户确认后批量写入。
  8. 字段映射可以保存为模板，便于后续复用。

导入后去重是必要能力：姓名 + 电话重复可自动合并；相似姓名、相同公司、相近电话等情况提示用户确认。

8.7 关系图谱可视化

  • 节点：联系人、项目/机会。
  • 边：介绍关系、合作关系、共同项目、共同话题、系统推断关系。
  • 支持按关系强度、资源标签、敏感级别、项目筛选。
  • 支持点击节点查看联系人名片。
  • 高敏感节点默认以代称展示，必要时仅显示存在关系而不显示明文信息。

图谱展示样式：

  • 实线：已确认关系。
  • 虚线：系统推断关系。
  • 灰色/待确认：需要用户确认的关系。
  • 不展示或隐藏：用户否认过的推断关系。

8.8 关系推断与确认

系统可以基于规则和 LLM 辅助推断潜在关系，但必须经过用户确认。

初版推断规则：

  • 同一公司的人互相认识：置信度高。
  • 同一行业 + 同一城市的人可能认识：置信度中。
  • 通过同一介绍人认识的人可能互相认识：置信度中。
  • 多次出现在同一项目或互动上下文中：置信度中。

用户操作：

  • 确认关系。
  • 否认关系。
  • 修改关系类型或强度。
  • 手动添加“A 认识 B”。

8.9 项目决策链路径生成

P1 增加路径生成能力。

输入：

  • 目标人。
  • 项目/机会。
  • 关键词或资源需求。

处理逻辑：

  • 从“我”出发查找路径。
  • 强关系优先。
  • 最近有互动的人优先。
  • 标签、项目、地域匹配度参与评分。
  • 限制最大跳数，初版建议 2~3 跳。
  • 对推断关系和已确认关系分别计算置信度。

输出：

目标：王局长（某园区管委会）

路径一（2跳，推荐）：
我 → 张明（直接认识）→ 王局长
依据：张明标签含“政府资源”，且最近 30 天有互动

建议行动：联系张明，询问是否认识王局长，请求引荐

8.10 自然语言查询（NLQ）

自然语言查询不应让 LLM 直接生成 SQL。推荐流程：

  1. 用户在统一入口用自然语言提问。
  2. 系统将问题解析为 QueryIntent 中间表示。
  3. 应用层对 QueryIntent 做白名单校验：字段、枚举、limit、排序均受控。
  4. 使用参数化 SQL 或安全查询构造器查询数据库。
  5. Windows 增强客户端可合并远程中低敏感结果和本地高敏感结果。
  6. 按关系强度、最近互动、话题匹配度等规则重排。
  7. LLM 只负责辅助解释和生成自然语言摘要，不直接接触任意 SQL 生成权限。
  8. 客户端展示匹配联系人、上次互动摘要、当前状态和建议下一步。

初版支持的查询类型：

类型示例
按标签/地域/关系强度查人“谁在上海做地产，和我关系比较近？”
按互动状态查人“最近 3 个月没联系但标记了待跟进的人有哪些？”
按话题查人“上次聊过融资的人里，还没跟进的有谁？”
按项目/需求匹配资源“这个懂车帝的投标，谁能帮上忙？”
按路径查人“我通过谁能联系到王局长？”
组合条件“做设计、关系强、最近一个月联系过的上海人”

9. 主动提醒机制

主动提醒从“后续演进”提升为 P1 设计。

提醒类型触发条件推送内容
关系冷却提醒联系人超过 N 天没有互动记录更新，且状态=待跟进“张明已 45 天没有互动记录——最近有联系吗？”
跟进提醒下一步行动有内容但超过 7 天未更新“你计划联系王总，有进展吗？”
新机会匹配用户新建项目节点时“图谱里有 3 个人可能和这个项目相关，要查看吗？”
关系激活建议强关系有至少一条互动记录且超过 60 天未更新“老李是你的核心关系，已超过 60 天没有互动记录——要不要顺手说一句？”

提醒频率：用户可选每日固定推送、信号触发或关闭。

10. 安全设计

10.1 身份认证与访问控制

  • 所有远程客户端必须登录后访问。
  • 服务端使用短期 access token + 可撤销 refresh token。
  • 高敏感数据查看需要二次确认，例如重新输入密码、WebAuthn、TOTP 或一次性确认。
  • 后续如支持多人使用，需要引入用户、角色、权限和资源隔离。

10.2 传输安全

  • 所有公网访问必须使用 HTTPS。
  • 上传音频、图片和查询请求不得走明文 HTTP。
  • API 默认启用 CSRF/CORS 策略，生产环境只允许可信域名。

10.3 数据加密

中低敏感远程数据：

  • 数据库所在磁盘启用服务端磁盘加密或云盘加密。
  • 电话、邮箱、备注、沟通原文、摘要、关系说明、下一步计划等字段加密存储。
  • 标签、状态、时间、关系强度等用于检索的低敏结构化字段可保留明文或保存规范化索引。
  • 原始音频和图片默认处理后删除；如保留，必须加密保存。
  • 数据库备份必须加密，并定期验证可恢复性。

高敏感本地数据：

  • 使用 SQLCipher 等方式本地加密。
  • 密钥不写入配置文件或日志。
  • 优先使用系统密钥链或用户主密码派生密钥。
  • 查看高敏感详情需要二次确认。

Open：高敏感数据备份、迁移和换机恢复方案暂未定。

10.4 敏感级别访问控制

敏感级别列表展示详情查看自然语言查询
低正常显示正常显示正常返回
中可显示代称和部分信息点击后显示完整信息返回结果但敏感字段脱敏
高显示代称 + 脱敏提示需二次确认默认折叠，提示“存在 N 位高敏感联系人，是否查看”

10.5 审计与日志可观测性

日志目标是方便排障、审计和性能观察，同时避免泄露隐私。

允许记录：

  • 请求 ID、用户 ID、接口名、状态码、耗时。
  • 查询类型、结果数量、候选数量。
  • 音频/图片大小、处理耗时、任务状态。
  • 敏感级别、是否触发二次确认、是否拒绝访问。
  • 错误摘要和错误类型。

禁止记录：

  • 密码、token、密钥。
  • 电话、邮箱、完整姓名。
  • 完整沟通内容、完整语音转写文本。
  • 原始名片图片内容或 OCR 全文。
  • 用户完整自然语言问题；可记录长度、查询类型和脱敏后的意图摘要。

13. 代码调整影响

从当前原型演进到 v1.3，代码需要做结构性调整：

  1. 后端从 Tauri Command 优先，逐步抽象出可被 REST API 和 Tauri 共用的 service 层。
  2. 增加 Intent Router，用于区分录入、更新、检索、路径生成和导入。
  3. 增加 Draft/Confirmation 流程，LLM 输出先成为草稿，用户确认后再写库。
  4. 扩展 Person、Relationship、Interaction 数据模型。
  5. 新增 Project/Opportunity、Reminder、ImportTask 字段映射等模型。
  6. 图谱展示需要支持已确认关系、推断关系、待确认关系和已否认关系的不同样式。
  7. 批量导入需要新增字段映射、预览、校验、去重和合并逻辑。
  8. Windows 增强客户端若承担高敏感本地库，需要保留或重构 Tauri 本地数据库能力。
  9. 所有新增 API 和任务处理都需要遵守隐私安全日志规范。

14. Open 问题

以下问题暂不在 v1.3 中强行定案，后续需要进一步确认：

  1. 高敏感数据只本地保存时，换电脑、电脑损坏、重装系统导致的数据丢失风险如何解决？
  2. 是否允许服务端保存高敏感数据的脱敏索引、不可逆摘要或加密备份？
  3. 高敏感互动记录是否绝对禁止上传服务端，还是允许用户显式选择加密备份？
  4. Windows 高敏感本地库由 Tauri 承担，还是由浏览器 + localhost helper 承担？
  5. 微信通讯录导入的技术可行性和合规边界。
  6. 多端使用场景下，是否需要多人账号、家庭/团队空间或权限分组？

15. 风险与应对

风险说明应对
分级存储复杂度同一应用同时访问本地和远程数据，查询和展示会更复杂明确数据边界，先支持简单合并展示
高敏感数据丢失本地不上传会带来换机和损坏风险标记 Open，后续设计加密备份和恢复机制
LLM 解析不稳定自然语言录入、更新和查询可能误判草稿确认、字段白名单、低置信度人工选择
表单依赖过重如果第一版只靠表单，维护成本高，用户容易放弃统一自然语言入口作为主流程，表单只兜底
ASR/OCR 资源消耗语音和图片识别需要 CPU/GPU 资源异步任务队列，限制文件大小，支持轻量模型
媒体文件泄露音频和名片图片包含敏感信息默认处理后删除；如留档，必须加密保存并审计访问
导入字段不匹配Excel/CSV 表头不统一，容易导入失败字段映射、预览、校验和模板复用
图谱推断误导AI 推断关系可能不准确推断关系默认待确认，用户可否认
部署复杂度Linux 服务端涉及 Docker、HTTPS、模型服务MVP 先支持单机 Docker Compose，AI 能力允许可选启用
