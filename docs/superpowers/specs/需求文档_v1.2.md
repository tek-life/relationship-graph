## 一、产品定位



**一句话**：把创始人/高管脑子里的人脉资产，变成可以用自然语言检索和调用的知识库，支持手机和电脑多端访问。



**核心场景**：



- “谁在建筑圈做过产业园，最近没联系的？” → 秒出结果

- “这个项目谁是决策人？我通过谁能搭上线？” → 自动生成关联路径

- 刚认识一个人，语音说一段话 → 自动生成关系卡片



**核心壁垒**：关系图谱不只是一个工具，它是用户完成内观之后，基于个人画像和决策风格构建的私有知识库。数据越积累，越懂这个用户，竞争对手无法复制这份积累。

## 一·五、架构决策：分级存储 \+ 远程服务端



> 已与技术伙伴对齐的架构方向，参照技术伙伴设计文档
> 
> 



采用\*\*分级存储\*\*策略——不同敏感级别的数据，走不同的存储路径：





|敏感级别|内容示例|存储方式|手机可访问|
|---|---|---|---|
|**高敏感**|核心合伙人、政商关系、家族关系|**本地加密，不上传服务端**|❌ 不支持|
|**中敏感**|行业人脉、潜在合作方|远程服务端（字段级加密）|✅ 支持|
|**低敏感**|公开信息、行业联系人|远程服务端|✅ 支持|





**架构形态**：



- 远程Linux服务端：业务逻辑、数据库、AI/ASR/OCR能力，Docker Compose部署

- Web/PWA客户端：Windows浏览器 \+ 手机浏览器，HTTPS访问服务端

- 高敏感数据例外：仅存本机，服务端不持有，客户端不上传



> ⚠️ \*\*红线\*\*：高敏感联系人数据绝不上传服务端，不可妥协。中低敏感数据走远程服务端，换取多端访问能力。
> 
>

## 二、数据架构：关系卡片



每个联系人对应一张关系卡片，字段按优先级分组如下：



### 基础信息 🔴 P0





|字段|类型|说明|
|---|---|---|
|姓名|文本|支持昵称/代称（aliases）|
|标签|多选|行业标签 \+ 能力标签 \+ 场景标签，用户自定义|
|关系强度|枚举|强 / 中 / 弱 / 待激活|
|敏感级别|枚举|高 / 中 / 低（决定存储路径）|





### 关系信息 🔴 P0





|字段|类型|说明|
|---|---|---|
|认识背景|文本|何时、何地、通过谁认识，敏感字段|
|认识渠道|文本|直接认识 / 谁介绍的（可关联到另一个联系人）|
|对方核心资源/能力|文本|他能提供什么，擅长什么|
|我能为他做什么|文本|价值互换视角|
|所属组织/公司|文本||
|职位/角色|文本||
|城市/地域|文本|用于地域检索|





### 互动记录 🔴 P0





|字段|类型|说明|
|---|---|---|
|上次互动时间|日期|自动计算“冷了多久”|
|上次互动内容|文本|摘要，敏感字段|
|当前状态|枚举|活跃 / 待跟进 / 冷却 / 已合作|
|下一步行动|文本|该做什么，敏感字段|
|互动历史|列表|所有互动记录，时间倒序|





> **⚠️ 互动记录的维护设计（重要）**
> 
> 
> 
> 互动主要发生在微信和电话中，系统无法自动感知。\*\*不能要求用户手动打开系统填写互动记录\*\*——这会让产品死在冷启动。
> 
> 
> 
> 采用 \*\*B\+C 组合方案\*\*：
> 
> 
> 
> **方案B：语音打标记（主要方式）**
> 
> 用户打完电话/见完面后，顺手语音说一句：
> 
> 
> 
> - “刚和张明聊了，他说下周来上海” → 自动更新互动记录
> 
> - 成本：约10秒，融入日常动作
> 
> - 
> 
> - **方案C：查询时顺手更新（兜底方式）**
> 
> - 用户查某个联系人时，系统检测到“上次互动时间较久”，主动询问：
> 
> - 
> 
> - “你上次和张明聊是45天前，最近有联系吗？”
> 
> - 用户回答后系统自动更新
> 
> 



### 关联关系 🟡 P1





|字段|类型|说明|
|---|---|---|
|认识的人|关联|他认识哪些图谱里的其他人|
|关联项目|关联|这个人和哪些项目/机会有关|
|关联路径|自动生成|我→A→B的几跳路径（见第五章）|





### 背景情报 🟡 P1





|字段|类型|说明|
|---|---|---|
|公开背景摘要|文本|联网搜集的公开信息|
|信息可信度|枚举|已确认 / 推断 / 待核实|
|最新动态|文本|最近的公开活动/新闻|
|核实建议|文本|哪些信息需要通过什么渠道确认|

## 三、数据录入：四种方式



### 🔴 P0 方式一：自然语言录入（核心交互）



用户说一段话，AI自动提炼成结构化关系卡片。



**输入示例**：



> “刚认识了一个人，他叫张明，是个做地产融资的，40多岁，上海人，是老李介绍的，上周饭局上见的，以后可能在园区项目上有合作机会。”
> 
> 



**AI自动提炼输出**：



```Plain Text
姓名：张明
行业标签：地产、融资
城市：上海
关系强度：弱（待培养）
认识背景：上周饭局，老李介绍
对方核心资源：地产融资
潜在合作：园区项目
当前状态：待跟进
```



**用户操作**：确认 / 用自然语言修改（“不对，他是做商业地产的” → AI自动更新对应字段）/ 补充信息



---



### 🔴 P0 方式二：语音录入



与自然语言录入完全一致，输入方式从打字变成语音。



**技术要求**：



- 手机端：录音后上传服务端，服务端Whisper/faster\-whisper转文字

- Windows端：录音或上传音频，同样走服务端

- 原始音频处理后默认删除，如留档则加密保存



---



### 🟡 P1 方式三：名片扫描录入（新增）



技术伙伴方案中有此功能，建议纳入P1：



- 手机端拍照 / Windows端上传图片

- 服务端OCR提取文字，LLM整理为结构化字段

- 客户端展示识别结果，用户确认后保存



---



### 🟡 P1 方式四：微信聊天记录导入



用户粘贴一段微信聊天记录，AI自动判断是否需要更新或新建联系人卡片。



- 识别联系人，更新互动记录

- 聊天记录中出现未在图谱中的人名且与具体事项相关联时，提示用户是否新建



---



### 🟡 P1 方式五：批量导入



- **表格文件**：支持CSV / Excel（\.xlsx）格式

- **手机通讯录**：支持iOS（vCard）/ 安卓导出

- **微信通讯录**：具体方案需技术侧评估可行性



**导入后去重**：自动检测姓名\+电话重复，相似姓名提示用户确认合并

## 四、自然语言检索





|用户输入|系统处理|返回内容|
|---|---|---|
|“谁在上海做地产，和我关系比较近？”|筛选：地产标签 \+ 上海 \+ 关系强度≥中|匹配联系人列表 \+ 上次互动摘要|
|“上周认识的那个地产圈的人叫什么来着？”|筛选：认识时间≈上周 \+ 地产标签|单个联系人卡片|
|“最近3个月没联系但标记了'待跟进'的有谁？”|筛选：上次互动时间\>90天 \+ 状态=待跟进|列表 \+ 建议下一步动作|
|“这个懂车帝的项目，谁能帮上忙？”|提取关键词 → 匹配相关标签|推荐联系人 \+ 关联路径|





**NLQ技术实现**（参照技术伙伴方案）：



- 用户问题 → 服务端解析为QueryIntent中间表示

- 应用层白名单校验（字段、枚举、limit、排序均受控）

- 参数化SQL查询，LLM不直接接触SQL生成权限

- 结果按关系强度、最近互动、话题匹配度重排

- LLM只负责生成自然语言摘要

## 五、关联线索与路径生成 🟡 P1



### 功能一：人脉网络关联图



**AI自动推断规则**（用户确认机制）：



- 同一公司的人互相认识（置信度：高）

- 同一行业\+同一城市的人可能认识（置信度：中，提示用户确认）

- 通过同一介绍人认识的人可能互相认识（置信度：中）



**用户操作**：确认 / 否认 / 手动添加“A认识B”



---



### 功能二：项目决策链路径生成



**路径生成逻辑**：



```Plain Text
从我出发
  → 第一跳：强关系节点中，谁认识决策人？
  → 第二跳：中等关系节点中，谁可能认识决策人？
  → 输出：最短路径 + 各路径置信度
```



**输出示例**：



```Plain Text
目标：王局长（某园区管委会）

路径一（2跳，推荐）：
我 → 张明（直接认识）→ 王局长
依据：张明标签含"政府资源"

建议行动：联系张明，询问是否认识王局长，请求引荐
```



> **技术注意**：路径计算需要图数据结构（Cytoscape\.js可视化）。需技术侧确认PostgreSQL与图计算层的数据同步策略。
> 
>

## 六、人物背景分析：联网搜集 \+ 服务端存储 🟡 P1



> 此功能不在MVP范围内，单独排期实现。
> 
> 



- 触发：在联系人卡片上点击“搜集公开背景”

- 搜集完成后存储在服务端，字段级加密

- 输出：结构化信息 \+ 可信度标注 \+ 最新动态 \+ 核实建议

## 七、主动提醒机制 🟡 P1



> 互动记录通过B\+C方案积累，初期数据稀疏时提醒以“建议”口吻出现。
> 
> 





|提醒类型|触发条件|推送内容|
|---|---|---|
|关系冷却提醒|联系人超过N天没有互动记录更新 且 状态=待跟进|“张明已45天没有互动记录——最近有联系吗？”|
|跟进提醒|“下一步行动”字段有内容但超过7天未更新|“你计划联系王总，有进展吗？”|
|新机会匹配|用户新建项目节点时|“图谱里有3个人可能和这个项目相关，要查看吗？”|
|关系激活建议|强关系\*\*有至少一条互动记录\*\*且超过60天未更新|“老李是你的核心关系，已超过60天没有互动记录——要不要顺手说一句？”|





**提醒频率**：用户可选每日固定推送（默认）/ 信号触发 / 关闭

## 八、数据安全设计



**架构原则**：高敏感数据本地化，中低敏感数据走远程服务端。





|数据类型|存储方式|加密|手机可访问|
|---|---|---|---|
|关系卡片（\*\*高敏感\*\*）|本地，不上传服务端|SQLCipher AES\-256|❌|
|关系卡片（中/低敏感）|远程服务端|字段级加密|✅|
|互动记录|远程服务端|字段级加密（原文、摘要、下一步计划）|✅|
|向量索引|远程服务端|服务端磁盘加密|✅|
|人物背景|远程服务端|字段级加密|✅|
|媒体文件（音频/图片）|处理后默认删除；留档则加密|加密存储|\-|





**传输安全**：全程HTTPS，API启用CSRF/CORS策略，生产环境只允许可信域名



**访问控制**：登录认证（短期token \+ 可撤销refresh token）；高敏感数据查看需二次确认



**备份**：服务端定期加密备份，用户可手动导出（加密ZIP包）

## 九、界面交互设计原则



**唯一入口**：一个对话框，用户说话/打字，系统判断意图



**意图识别要求**：



- **系统必须容错**——用户无需记住任何触发词或格式

- 三种意图准确区分：

    - **录入**：“张明啊，做地产的，刚认识” → 新建联系人卡片

    - **检索**：“帮我查一下张明” / “谁认识做园区的” → 检索模式

    - **更新**：“张明上周来上海了” → 更新对应联系人互动记录

- **边界判断规则**：已有联系人姓名\+时间/事件描述 → 优先识别为更新；未知人名\+标签描述 → 录入；疑问句或条件描述 → 检索

- 修改卡片也用自然语言，AI自动更新对应字段，不弹出表单



**✅ 应该有的交互**：



- 卡片确认：AI提炼完后展示，一键确认或用自然语言修改

- 关联推断确认：AI推断“A认识B”后，用户一键确认/否认

- 路径展示：图形化展示“我→A→B→目标”的路径



**❌ 不应该有的交互**：



- 填写表单 / 下拉菜单选分类 / 必填字段提示 / 任何需要“学习”才能用的操作

## 十、技术栈



参照技术伙伴设计文档，已对齐如下选型：





|层级|选型|说明|
|---|---|---|
|前端|React \+ TypeScript \+ Vite \+ Tailwind|Web/PWA优先|
|客户端形态|Web/PWA（Windows浏览器 \+ 手机浏览器）|后续可封装桌面壳或App|
|后端|Rust Axum / FastAPI / NestJS（技术侧评估）|REST API优先|
|数据库|PostgreSQL优先；MVP可先用SQLite|字段级加密|
|LLM|Ollama / vLLM / OpenAI\-compatible API|服务端部署|
|语音识别|Whisper / faster\-whisper|服务端部署|
|名片OCR|PaddleOCR / Tesseract \+ LLM结构化|服务端部署|
|图谱可视化|Cytoscape\.js 或 vis\-network|前端渲染|
|部署|Docker Compose \+ Caddy/Nginx \+ HTTPS|Linux服务端|
|日志|structured logging \+ request\_id \+ audit log|不记录敏感内容原文|
